# v0.6 设计:Controller ↔ Worker 通信增强

> 状态:实施完成(2026-10-30,分支 `release/0.6.0`;评审见 [v0.6-design-review.md](./v0.6-design-review.md),实施按其修订意见收敛范围)
> 对应 README Roadmap 主题:执行增强(通信面)。
> 范围:**仅 2a**(controller → 运行中 worker 补充指令的时效)+ **2b**(worker → controller 阻塞式提问)。WAY-N 编号移出本版(见 §8)。

## 1. 背景与目标

2a 与 2b 都是**正确性修复**,不是功能叠加:前者修"补充指令投递不可靠"(延迟、静默丢弃、假回执),后者补"worker 执行受阻时唯一的求助通道"。

### 1.1 现状调研结论(2a)

controller 侧统一入口是 `chat_worker` → 引擎 `sendMessageToWorker` → `acceptMessage`,之后两种 worker 分叉:

**Puppet(拉模式)**:消息进 `WorkerState.inbox`(**仅内存,不持久化**——持久化路径只有 runtimeState 与 conversation),worker 必须主动调 `check_controller_messages` 才能读到。时效取决于 LLM 何时自发调用——prompt 只有软性指引,工具描述写着 "call periodically / it is cheap",实测高频空查,每次空查烧一整个步,却没换来及时性。另有一个丢失口:multiStage worker 接新任务时 inbox 未读不注入。

**Claude Code(推模式,但推在回合边界)**:消息进内存队列,`buildPromptIterable` 作为 streamInput 的下一条 yield 给 SDK;SDK 只在当前回合结束时才拉取下一条输入,消息延迟 = 剩余回合长度。任务结束时 `handleResultMessage` 直接 `flushMessageQueue()`,Claude 先判定完成的场景下 controller 指令被**静默丢弃**,而 `chat_worker` 已返回 "Message delivered"。

**投递判定的真实漏洞(评审 2.2,比上述更根本)**:`removeWorkerTracking` 用 `setTimeout(0)` 延迟删除 worker,此窗口内 `sendMessageToWorker` 依据 workers Map 存续仍返回 true——消息投给一个即将消失的 worker,静默丢失而回执成功。根因是**状态判定**,不是投递通道。

SDK 能力面(0.2.98,已读 `.d.ts` 确认):Query 对象无 sendMessage 类 API;streamInput + `interrupt()` 是官方 steering 通道;`createSdkMcpServer` 的 SDK MCP 调用**默认 60s 超时**(sdk.d.ts:405-406,超过需覆盖 `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT`);deny 类 PermissionResult 支持 `interrupt: true`,`getContextUsage()` 可取上下文占用——后两者本版不用,记录备查。

### 1.2 现状调研结论(2b)

worker 上行只有 `update_progress`(单向进度)、`done`/`fail`(终态)、`permission_request`(宿主中间件代发)。没有任何"worker 主动提问并等待回复"的通道。permission 链路提供了完整的阻塞应答范式:信号 + pending Map + Promise resolve + controller 应答工具 + 超时兜底 + abort cleanup。2b 与 permission 应抽**共用"阻塞请求"抽象**(pending map + 超时 + cleanup 三件套),避免复制后漂移(评审 3.2)。

## 2. 2a — Puppet:prepareStep 注入

### 2.1 机制

- `streamText` 增加 `prepareStep` 选项(AI SDK 6.x 稳定 API;base-agent 透传,仅 worker 使用)。每步 LLM 请求前回调,入参含当步将发送的 messages。
- 回调内 drain inbox:新消息转 user message(`[Controller message] ...`),返回 `{ messages: [...当步 messages, ...injected] }`;无新消息返回 undefined(零开销)。
- **关键语义(已读 SDK 6.0.x 实现确认)**:每步基准为 `stepInputMessages = [...initialMessages, ...responseMessages]`(node_modules/ai/dist/index.mjs:4522),prepareStep 的 messages 覆盖**仅作用于当次请求**(index.mjs:4539-4540)。因此注入消息不会自动延续——闭包持有 `injected[]` 每步重 append,指令自注入起持续在场于上下文尾部("最新指令在底部"的聊天语义)。该重注入**必要且安全**,不会重复累积(基准不含注入项)。代价:指令消息在任务剩余步持续占 prompt(几十 token/条,可忽略)。
- **注入消息必须同步写入 `state.conversation` 的 User entry(actor: controller)**——机制原因:`context-manager.getMessages()` 每次从 conversation 重建消息,只改 prepareStep 的内存消息而不落 entry,会出现"当前任务收得到、进入下一 stage 就丢"的隐蔽 bug(评审 2.1)。两条路径都写,缺一不可。
- 只在尾部 append user 消息,不动 assistant/tool 消息,tool-call 配对无风险。
- 时效 = 下一个 LLM 步边界;工具执行期间(长 bash)等待工具结束,任何注入方案相同。
- **不做**宿主驱动逐步循环重构:prepareStep 覆盖了注入需求,循环结构、watchdog、聚合、onStep 记录全部不动。

### 2.2 收尾清理

- 删除 `check_controller_messages` 的真实实现,但**保留一版返回 `[DEPRECATED] No longer needed — controller messages are injected automatically` 的占位工具,跨一个 minor 版本再移除**(评审 2.4:旧任务 description 文本可能内嵌"定期调用"类指引,prompt 每次 spawn 现建不会残留,但历史任务的 description 会)。
- worker prompt 的 "Checking for messages" 段替换为:"controller 可能在执行中注入 `[Controller message]` user 消息,视为任务指令的权威更新"。
- multiStage worker 接新任务(`run()` 再入)时,开场先注入 inbox 未读(inbox 不持久化,此路径只覆盖同进程内的 stage 切换;进程重启后 running 任务本就被判失败,无 resume 重放问题)。
- 任务收尾 inbox 仍有未读 → 信号回告 controller `message_undelivered (task finished)`,由 controller 决定是否重派;不再静默。

## 3. 2a — Claude Code:丢弃修复 + interrupt

- **修静默丢弃(先做,bug 级)**:`handleResultMessage` 时队列非空 → 不 flush,向 controller 发 `message_undelivered` 信号(worker finished before reading);对 idle 的 multiStage worker 重派成本很低。abort(controller 主动取消)维持现状。
- **interrupt 投递**:`acceptMessage` 入队后调用 `this._activeQuery.interrupt()`——打断当前回合,SDK 立即回来拉下一条输入。`stream` 由 run() 局部变量提升为实例字段,run 结束清空。
- **interrupt × pending permission 的安全护栏(评审 1.1)**:immediate 模式 interrupt 前检查 `_pendingPermissions`,非空则将 interrupt 排队到 permission resolve 之后执行——pending 等待期间打断的后果(孤立 tool_use / promise 永不结算)无法从代码证明,实现前必须 PoC(§6.1),PoC 结论若显示可安全打断再放宽。
- **策略** `interruptOnMessage`:`'immediate'`(默认)/ `'turn-end'`(维持现状语义)。配置于 worker 定义。
- idle 期间到达的消息,下一阶段 run() 时前置合并进初始 prompt(现状要等新任务第一个回合结束)。

## 4. 2a — chat_worker 投递语义

- **投递判定修正(评审 2.2)**:引擎 `sendMessageToWorker` 改为依据 `activeWorkers` 运行态判定,而非 workers Map 的存续——消除 `setTimeout(0)` 删除窗口内"投给将死 worker 却回执成功"的假阳性。
- 返回值改为真实状态:puppet → `delivered (read at next step)`;claude-code → `queued (will interrupt)` / `queued (read at next turn)`;worker 不在运行态 → `[ERROR] Worker not running`。
- TUI `✉ 发送给 ...` 行状态文案跟进("已送达"改为实际投递语义)。

## 5. 2b — ask_controller / respond_inquiry

### 5.1 共享脊柱(与 permission 共用"阻塞请求"抽象)

| 组件 | 内容 |
| --- | --- |
| 信号 | `worker_inquiry`:{inquiryId, workerId, taskId, taskTitle, workerType, emoji, question, context?} |
| worker 工具 | `ask_controller(question, context?)`:发信号 → 阻塞请求(共用抽象)→ 答案作为工具结果;超时(5 min,对齐 permission)返回 `[TIMEOUT] No answer — use your best judgment` |
| controller 工具 | `respond_inquiry(inquiryId, answer)`,镜像 `respond_permission`;worker 已中止 → **结构化错误**(含原因),而非裸 false(评审 2.3) |
| 引擎 | worker 暴露 `inquiryHandler { resolveInquiry, cleanup }`(同 `permissionHandler` 形态);abort 时 cleanup 全量 resolve("worker aborted") |
| RPC | 新增 `respond_inquiry` 命令,TUI / Web 双端可应答 |

**死锁免疫**:controller loop 阻塞于 `waitForSignal()`,`worker_inquiry` 入队即唤醒——信号驱动天然打破互等环。

**超时主动回报(评审 2.3)**:inquiry 超时(以及 worker 侧 cleanup)时向 controller 发 `inquiry_timeout` 信号——worker 自行继续的决定对 controller 可见,不再等到 respond_inquiry 才发现。

### 5.2 Puppet 侧

普通工具进 `createWorkerTools`,零结构改动(工具执行期即暂停点,不依赖 prepareStep);`recordToolCalls` 自动落审计。prompt 新增 "Asking the controller":**仅当执行受阻、继续有浪费风险、环境与指令冲突时问;能自主决定的不要问**。措辞是防滥用的关键,评审重点。

### 5.3 Claude Code 侧

`createSdkMcpServer({ tools: [ask_controller] })` 注册为进程内 MCP 工具——模型在工具目录中真实可见,不依赖 prompt 约定的虚拟工具名;execute 阻塞在宿主代码。

**超时必须显式处理(评审 1.2,已证实)**:SDK MCP 调用默认 60s 上限(sdk.d.ts:405-406),而 ask_controller 最长阻塞 5 分钟。方案:spawn claude 进程时注入 `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT` 环境变量调高(如 360s);仍需 PoC 确认行为(§6.2)。若 PoC 证伪,fallback 为改走宿主回调通道(与 permission 同路的拦截模式)。

问答审计:controller 侧(SignalEntry + respond_inquiry 记录)之外,worker conversation 落一条 System entry 记问答摘要(评审 3.1,复盘用;worker 对话记录只写不读,无恢复语义负担)。

### 5.4 边界

- LLM idle watchdog 已在工具执行期暂停(0.5.2 行为),ask_controller 自动豁免;`idleTimeoutMs` 仅作用于停泊 worker——各补测试断言。
- 升级链:默认 controller 直接答复;决策权属用户时(改需求、动危险资源)controller 经 `inquire` 转人类,拿到答案再 `respond_inquiry` 回 worker。
- 一步内多次 ask 支持;迟到回复(超时后/中止后)返回结构化错误,controller 得知 worker 已按自己的判断继续。

### 5.5 TUI

复用 0.5.2 结构化行:`? 🧸 <task> 提问 #xxxx`(问题预览次行);`✔ 已答复 ... #xxxx`;超时行 `⏱ 提问超时(worker 自行继续)`。

## 6. 实现前必须完成的三个验证(评审 §六)

1. **PoC:interrupt × 挂起 permission**——canUseTool pending 期间、工具执行中调用 `interrupt()`,确认是否留下孤立 tool_use 及下一轮真实行为,据此确定安全插入点(§3)。
   *实施状态:已按保守假设落地护栏(pending 非空时排队到 resolve 后);确认脚本 `scripts/poc-interrupt-permission.mjs`,需本地真实 claude CLI 运行,PoC 结论若证明可安全打断可放宽。*
2. **PoC:MCP 工具长阻塞**——进程内 MCP 工具 execute 阻塞超过默认超时是否被掐断;`CLAUDE_CODE_STREAM_CLOSE_TIMEOUT` 覆盖是否生效;确定 ask_controller 的实现通道(§5.3)。
   *实施状态:SDK 官方注释已证实 60s 默认上限(sdk.d.ts:405-406);实现已按文档注入 env 覆盖(360s)。确认脚本 `scripts/poc-mcp-timeout.mjs`(对照/覆盖两档),需本地真实 claude CLI 运行。*
3. **哨兵测试雏形:e2e 多步任务注入在场性**——断言注入消息逐轮在场且幂等,后续 SDK 升级时该测试先红(§7-1)。
   *实施状态:已完成——`e2e/scenarios/worker-comm.test.ts` 注入场景 + `src/services/agents/utils/__tests__/inbox-injection.test.ts`。*

## 7. 验收标准(每条可客观判定)

1. 注入在场性单测:注入后,逐条断言每一轮发给模型的 messages 尾部仍含该指令,且同一条指令不重复出现两次以上。
2. 无消息零覆盖单测:inbox 为空时 prepareStep 返回 undefined,实际请求的 messages 与未启用该选项时逐字节相等。
3. 静默丢弃 e2e:任务完成瞬间队列仍有未读消息,controller 收到 `message_undelivered`,chat_worker 不再返回虚假的 delivered。
4. 工具执行中收指令 e2e:长耗时 bash 期间发送指令,任务要么读到并继续、要么干净失败;进程无未捕获异常,abort 后 pending Map size = 0。
5. inquiry 四路径单测:正常 resolve / 超时返回 `[TIMEOUT]` 并继续 + `inquiry_timeout` 信号发出 / abort 时全部 resolve 且清理干净 / 迟到的 respond_inquiry 返回结构化错误。
6. 全环 e2e:worker 提问 → controller 应答 → worker 完成,带超时上限,全程无死锁。

回归:全量单测 + CI(lint / test / build / e2e)。

## 8. 明确不在本版

- **WAY-N 任务编号(评审 §四,移出)**:短后缀体系(`id.slice(-4)`)已覆盖当前指代需求;workspace counter 引入持久化、跨进程互踩(session-index 明确支持多实例无锁并发)、损坏自愈、旧条目回退四类新问题,与 2a/2b 的正确性修复性质不同,混版稀释评审与回归。后续若仍需要时间序语义,优先做**展示层按 createdAt 排序编号**(纯只读,无落盘,同毫秒以 id 字典序 tie-break)。
- 任务依赖(blockedBy)、任务组、结构化规划、worktree 隔离、MCP 挂载、worker 间直接消息协议(共享文件 + controller 中转够用)。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| prepareStep 语义随 SDK 升级漂移(基于 6.0.x 读实现确认) | 锁 ai 依赖小版本区间;验收 1 的在场性测试作为升级哨兵 |
| interrupt 与挂起 permission 的交互未证明 | 实现前 PoC(§6.1);护栏:pending 非空时排队到 resolve 后再 interrupt |
| MCP 工具 60s 默认超时掐死 ask_controller | `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT` 显式覆盖 + PoC(§6.2);fallback 走宿主回调通道 |
| ask_controller 滥用拖慢任务、controller 变瓶颈 | prompt 措辞约束;上线后观察频率,必要时加每任务次数上限 |
| 与 permission 链路共享范式,回归面重叠 | 抽共用阻塞请求抽象,permission 既有行为不变;inquiry 独立用例;全量回归 |
| 旧任务 description 内嵌已废弃工具指引 | 占位工具跨一个 minor 版本(§2.2) |
