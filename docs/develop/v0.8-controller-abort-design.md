# v0.8 设计：ESC 中止 Controller 回合（thinking / 流式输出）

> 状态：已实施（分支 `fix/esc-abort`，基于 origin/main；质量门槛 `npm run lint` / `npm test`（1053 passed）/ `npm run build` 全绿）。
> 范围：仅 controller 自身回合的中止。不触碰 worker 任务生命周期、不重构流式渲染 / 消息存储 / 输入框其他行为。

## 1. 问题与复现步骤

设计意图：输入框内按 ESC 立即中止 controller 当前的思考与流式输出。

复现（当前 main）：

1. 启动 TUI，向 controller 发一条需要长回答的消息。
2. controller 处于 `busy`（spinner 转动、流式文本增长）时在输入框按 ESC。
3. 观察：流式输出继续，直到自然结束；ESC 唯一效果是关闭可能开着的 overlay（或清空输入草稿）。

产品要求（约束，不再讨论）：

1. 中断后已产出的部分输出保留为一条截断消息，不丢弃、也不再继续流。
2. 中断必须留下显式中断记录，下一回合 controller 必须知道"上一轮被用户打断"，不能靠消息长度推断。
3. ESC 只中止 controller 自身的思考/输出，绝不取消正在运行的 worker 任务。
4. ESC 时一个 token 都没输出 → 不落空 assistant 消息（provider 侧对空内容会报错），只落中断标记。

## 2. 根因（证据：文件:行）

**ESC 被消费但从未连到 controller。**

- ESC 按键处理：`src/tui/components/input-area.tsx:199-215` —— 依次处理：有选区 → 仅取消选区；有 / 建议面板 → 丢弃草稿；否则调用 `onEscape?.()` 并 reset 草稿。ESC 事件本身已在此被消费，不会冒泡。
- `onEscape` 的唯一消费者：`src/tui/pages/controller-page.tsx:138` 把它接到 `dismissOverlay`（关闭 overlay 面板）。**没有任何路径通向 controllerAgent。**
- 对照：Ctrl+C 在 busy 时已有中止意图 —— `src/tui/app.tsx:29-34` 调 `supervisor.controllerAgent.abort()`；RPC 通道也已存在（`src/rpc/protocol.ts:70`、`src/server/wayang-server.ts:162-165`、`src/client/remote-supervisor.ts:49-52`），但同样从未被 ESC 使用。

**且现有 `abort()` 通道有一个潜在致命缺陷，直接复用会永久废掉 controller：**

- `BaseAgent.abortController` 是 agent 生命周期级的（`src/services/agents/base-agent.ts:84`），`abort()` 后 signal 不可逆（:282-284）。
- `streamLoop` 每次调用检查 `this.abortController.signal.aborted`，若已 aborted 则本次 callAbort 立即中止（:110-112），textStream 抛错后在 catch 中因 agent signal aborted 而干净返回空结果（:224-226）。
- 后果：controller（长寿命 agent）一旦被 abort 一次，**之后所有回合都立即空返回**——今天 app.tsx:32 的 Ctrl+C-while-busy 路径就踩在这个坑上（用户按一次 Ctrl+C 中止后，controller 永久哑火）。worker 不受影响（一次性 agent，abort 即 dispose，`src/services/agents/worker-agent.ts:180` 依赖该永久语义）。

**回合执行链路（中止需要插入的位置）：**

```
ControllerLoop.start (controller-loop.ts:80-121)
  └─ await controllerAgent.run(signals)          ← 回合入口，busy=true (controller-agent.ts:149-156)
       └─ _run (controller-agent.ts:158-242)
            ├─ 生成 turnId / TurnEnvelope (:165-177)
            ├─ 信号 → conversation 落盘 (:184-188)
            ├─ 清 streamingEntries、创建流式占位 entry (:191-194)
            ├─ streamLoop({..., onStep}) (:196-223)
            │    └─ BaseAgent.streamLoop (base-agent.ts:102-266)
            │         ├─ callAbort = per-call AbortController (:108)
            │         ├─ agent abortController → callAbort 转发 (:110-114)
            │         ├─ streamText({ abortSignal: callAbort.signal }) (:194)
            │         └─ abort → textStream 抛错 → catch: agent signal aborted ⇒ 干净返回 {text:''} (:224-226)
            └─ for await 聚合 chunk → streamingEntry.message.content (:225-237)
```

中止通道结论：**AbortController 通道已存在且贯通**（agent abortController → callAbort → streamText abortSignal → 干净返回），缺的只有两块：(a) ESC 到 `abort()` 的接线；(b) agent 级 controller 的 per-run 复位（否则中止一次即永久失效）。

**会话落盘（中断记录的落点）：**

- controller 消息历史：`<sessionDir>/conversation.jsonl`，append-only，`state.append('conversation', entry)` 即同步写盘（`src/infra/state/base-state.ts:59-75` → `src/infra/state/persistence/jsonl-file.ts:40-46` `appendFileSync`）。
- 条目为四类 union（`src/types/conversation.ts:144-148`）：UserEntry / AssistantEntry / SignalEntry / SystemEntry，共享 envelope（turnId/rootTurnId/actor/…，:108-130）。
- 流式期间的部分文本只存在于 `dynamicState.streamingEntries`（内存，不落盘，controller-agent.ts:225-237）；完整 step 在 onStep 时才落盘（:205-222）。**中断时必须把 in-flight 的部分文本手动落盘。**
- LLM 回放重建：`ContextManager.getMessages()` → `conversationToSdkMessages()`（`src/services/agents/utils/conversation-to-sdk-messages.ts`）。关键行为：
  - SystemEntry 被整体跳过（:103-105，注释只提 compact marker）——**新中断标记若用 SystemEntry，必须在 converter 特判，否则下一回合看不到。**
  - SignalEntry 回放为 `[WORKER PROGRESS SIGNAL: <SUBTYPE>] content`（:107-115）——用户中断套这个标签语义错误。
  - 空 content 且无 toolCalls 的 AssistantEntry 不产生任何消息（:64-69）；但 thinking 模型会回填 `' '` reasoning（:44），产生近乎空的 assistant 消息，这正是"provider 对空内容报错"的风险面（DeepSeek/GLM 系）。孤儿 tool-call 已有占位结果机制（:84-99），abort 场景的 SDK 回放合法性已覆盖。

**worker 侧对照（"中止是一等状态"的参照）：**

`engine.cancel()`（`src/services/task-execute-engine.ts:186-226`）：abort worker（:193）→ 任务状态迁移 `cancelled`（:194）→ 抑制被中止 worker 的假 failed 信号（:198）→ 发出专属 `task_cancelled` 信号（:199, :234-255）→ 落为 SignalEntry subtype=`task_cancelled`、content=`[TASK CANCELLED] …`（controller-agent.ts:656-665）→ 会话索引把该回合推导为 `cancelled` 终态（conversation-index.ts:92-97, 273-281, 293-305）。本方案对照该模式：显式中止记录 + 非失败终态 + 下一回合可见。

## 3. 方案

分层设计如下。争议点在 §3.6 单独列出选项与推荐。

### 3.1 状态模型：回合的 aborted 状态如何表示与流转

- **中止原语**：沿用 AbortController（AI SDK `streamText` 原生支持 `abortSignal`）。`BaseAgent.abortController` 从 `readonly` 改为可变，新增 `protected resetAbortController()`；`ControllerAgent.run()` 在回合开始时复位。这样：
  - 中止只作用于当前回合（下一回合天然全新）；
  - `streamLoop` 既有的转发（base-agent.ts:110-114）与干净返回（:224-226，含回归测试 base-agent.test.ts:328）零改动直接复用；
  - worker 不复位，永久 abort 语义不变；
  - 顺带修复 app.tsx Ctrl+C-while-busy 的永久哑火 bug（该路径与本方案共用 `abort()`）。
- **回合内流转**：`_run()` 的流式循环正常结束后检查 `this.abortController.signal.aborted`——为真即本回合被用户中止，进入中断落盘路径（§3.2）。abort 发生在流式任何阶段（含首个 token 前、工具执行中）都收敛到同一检查点；`streamLoop` 保证 abort 后生成器干净返回而非抛错。
- **busy**：`run()` 的 finally 照旧置 `dynamicState.busy=false`，TUI spinner 自然停。

### 3.2 落盘格式

中断最多落两条记录，顺序固定，均带被中止回合的 TurnEnvelope（turnId/rootTurnId/actor）：

1. **截断 assistant 条目**（仅当 in-flight 部分文本 `trim()` 非空）——复用流式占位 entry 的 uuid 与 content，追加 `interrupted: true` 标记：

```json
{
  "type": "assistant",
  "uuid": "s-abcd1234",
  "parentUuid": null,
  "sessionId": "…",
  "timestamp": "2026-11-03T08:00:00.000Z",
  "message": { "role": "assistant", "content": "已流出的部分文本…" },
  "interrupted": true,
  "timing": { "startedAt": "2026-11-03T08:00:00.000Z", "endedAt": "2026-11-03T08:00:05.000Z" },
  "v": 1, "parentId": "…", "turnId": "turn-…", "rootTurnId": "turn-…",
  "actor": { "kind": "controller", "id": "agent-…" },
  "startedAt": "…", "endedAt": "…"
}
```

   字段说明：`interrupted: true`（AssistantEntry 新增可选字段）标识"该 step 输出被用户截断，非模型自然结束"；无 `finishReason`/`usage`/`toolCalls`（SDK 未完成该 step，不伪造）。
   去重护栏：仅当该 uuid 不已在 conversation 中（未被 onStep 落盘）才追加，防止"abort 恰落在 step 完成后"的窗口重复。

2. **中断标记 SystemEntry**（无条件落，含零输出场景）：

```json
{
  "type": "system",
  "uuid": "sys-abort-…",
  "parentUuid": null,
  "sessionId": "…",
  "timestamp": "2026-11-03T08:00:05.000Z",
  "subtype": "interrupted",
  "content": "Response interrupted by user.",
  "startedAt": "2026-11-03T08:00:05.000Z",
  "endedAt": "2026-11-03T08:00:05.000Z",
  "v": 1, "parentId": "…", "turnId": "turn-…", "rootTurnId": "turn-…",
  "actor": { "kind": "user", "id": "user" }
}
```

   `ESystemSubtype.Interrupted = 'interrupted'` 为新增枚举值。

**LLM 可见性**（下一回合必须知道被中断）：`conversationToSdkMessages` 对 `subtype === 'interrupted'` 的 SystemEntry 特判，回放为一条 system 消息（其余 SystemEntry 维持跳过）：

```
[USER INTERRUPT] The user aborted the previous response with ESC while it was streaming. Any assistant text immediately before this marker is a truncated partial — treat it as incomplete context, not as a finished answer or instructions.
```

标签样式与 SignalEntry 的 `[WORKER PROGRESS SIGNAL: …]` 同构。`allowSystemInMessages` 已开启（base-agent.ts:203），无需其他开关。

### 3.3 TUI 呈现

- **接线**：`controller-page.tsx` 的 `onEscape` 改为：overlay 开启 → 仅关 overlay（保持屏幕上 "(esc to dismiss)" 提示的既有语义）；否则 `busy` → `supervisor.controllerAgent.abort()`（本地/远程同一 facade，remote-supervisor.ts:49-52 已实现）。决策逻辑抽为纯函数 `resolveEscapeAction({ overlayOpen, busy }) → 'dismiss-overlay' | 'abort' | 'none'` 便于单测。InputArea 本身零改动（ESC → onEscape 既有路径，input-area.tsx:199-215）。
- **中断标记行**：SystemRow 新增 `interrupted` 分支，`⊘ Response interrupted by user.`，灰色低调呈现（用户自己按的，不是错误）。
- **截断条目行**：DisplayItem 透传 `interrupted`，AssistantStepRow 在该 step 末尾追加一行 dim `⏹ interrupted`，明确标出"哪一步被截断"。
- **流式区**：中断落盘后清空 `dynamicState.streamingEntries`，spinner 因 busy=false 停止；截断条目进入 conversation 静态区正常渲染，无空帧。

### 3.4 零输出边界

`in-flight 部分 trim 为空`（含纯空白 chunk、abort 早于首 token、abort 落在两 step 之间）→ **不落 assistant 条目**，只落 §3.2 第 2 条中断标记。依据：conversation-to-sdk-messages.ts:44 的 thinking 模型回填会制造近空 assistant 消息，DeepSeek/GLM 类 provider 会拒绝整包请求；:64-69 证明空条目在回放中也不产生任何信息，落了只有风险没有收益。

已知限制（记录，不处理）：流式循环只消费 `textStream`（base-agent.ts:216），thinking 的 reasoning 增量在 step 完成前不可得，中断时部分 reasoning 丢失——截断条目只保留文本部分。

### 3.5 与后续回合的衔接

- **时序**：ControllerLoop 是单线程顺序循环（controller-loop.ts:80-121），`run()` 被 await，结构上不存在两个并发回合。ESC 中止后当前 run 迅速收敛返回 → loop-end → `waitForSignal()`；期间用户立即发送的新消息已在队列，下一轮 dequeue 即开启新回合。中断后紧接着发消息是安全且推荐的用法。
- **worker 不受影响**：ESC → `controllerAgent.abort()` 全链路不触碰 engine（无 `cancel`/`abortAll` 调用）；回合内已派发的任务照常运行，其完成/失败信号入队，由后续回合处理。被中止回合在会话索引中若有未完结任务仍推导为 `running`（conversation-index.ts:295-296 优先级），符合真实状态。
- **工具执行中 abort**：controller 的同步工具（search_files 等）不被打断（streamLoop 的工具包装只暂停看门狗，不检查 abort，base-agent.ts:143-153），工具完成后流随即因 abort 终止；已完成的 step 照常由 onStep 落盘。ai@6 的 finish-step 在该 step 工具执行完毕、tool-result parts 入队之后才入队，因此 abort 落在工具执行期间时，onStepFinish 仍携带完整 toolCalls+toolResults——含 add_task 的 taskId 关联——必须落盘，否则被中断回合在会话索引中丢失未完结任务、被推导为 cancelled，worker 完成信号将指向对话中不存在的任务。极端窗口（abort 后 step 恰好完成）由 §3.2 的 uuid 去重护栏兜底：完整 step 落盘并消费流式占位 uuid，recordUserAbort 不再重复追加部分文本。onStep 守卫因此不检查 abort signal（signal 在 ESC瞬间即置位，早于该 step 处理），只丢弃本回合中断记录已落盘之后到达的 step-finish。
- **prompt cache**：下一请求的前缀（system prompt + 既有消息序列）与中止前完全一致，截断条目 + 中断标记只是新增后缀——与任何正常回合新增内容对缓存的影响同类，无额外失效。相比"让回合跑完"，中断反而让后缀更短。
- **回放合法性**：截断条目为纯文本 assistant 消息（无孤儿 tool-call）；已完成的 tool step 带完整 toolCalls+toolResults；现有孤儿占位机制（conversation-to-sdk-messages.ts:84-99）覆盖其余 abort 窗口。
- **会话索引终态**：携带 `interrupted` 标记的回合推导为 `cancelled`（复用现有非失败终态，conversation-index.ts:299-300），与 worker 侧 task_cancelled → cancelled 的语义对齐；有未完结任务时仍为 `running`。

### 3.6 争议点：选项 / 推荐 / 理由

**A. 中断标记放 conversation 内（消息元数据）还是独立事件流？**

- 选项 1（推荐）：conversation 内 —— 截断 assistant 条目（元数据 `interrupted`）+ `interrupted` SystemEntry。
- 选项 2：独立事件流（如 events.jsonl）。
- 理由：下一回合的上下文由 `getMessages()` 从 conversation 重建，这是唯一回放源；独立流需要第二条读取/合并路径，且 resume/crash-recovery 只读 conversation.jsonl——标记必须进会话文件才能满足"下一回合知道"。审计与 TUI 也都已在消费 conversation 条目。独立流没有任何既有消费者，纯属新增 plumbing。

**B. 是否复用现有 signal 体系（SignalQueue）承载中断？**

- 选项 1（推荐）：不复用。ESC 直接调 `controllerAgent.abort()`，中断记录由被中止回合自身在 run 内落盘。
- 选项 2：入队一个 `user_interrupt` 信号，由 signalToEntry 落为 SignalEntry。
- 理由（独立判断后仍与提问者倾向一致）：
  1. **拓扑不匹配（决定性）**：SignalQueue 是"唤醒空闲循环"的队列——信号由**下一轮** `dequeueUnread` 消费；而当前回合正阻塞在 `run()` 内 await 流。走信号无法打断在飞流，只能等它自然结束，等于没实现需求。中断必须直达在飞的 AbortController。
  2. 语义不匹配：信号是 worker/system 的"汇报"，作为上下文被消费；中断是控制面事件，作用于当前回合本身。
  3. 落盘形态不匹配：SignalEntry 回放为 `[WORKER PROGRESS SIGNAL: …]`（conversation-to-sdk-messages.ts:107-115），用户中断套该标签语义错误；若为它特判标签，改动量与 SystemEntry 方案相当却保留了错误的类型语义。
  - SignalEntry vs SystemEntry 的选择：worker 侧取消用 SignalEntry 是因为它天然经由队列产生；本方案的中断由回合自身产生（不经队列），SystemEntry（"系统事件"——与 compaction marker 同类）+ converter 特判是更贴切的载体。

**C. 中止通道用 AbortController 还是现有机制？**

- 选项 1（推荐）：AbortController（per-run 复位，见 §3.1）。
- 选项 2：`SystemContext.abortController` —— 否决：那是进程级关停信号，abort 它会触发 ControllerLoop 的 `break`（controller-loop.ts:80,109）直接杀死循环。
- 选项 3：`streamText` 返回对象的 reader/流级 cancel —— 否决：streamLoop 只迭代 `textStream`，不持有可 cancel 的 reader 句柄；且绕过既有的干净返回语义，需要新错误处理路径。
- 理由：AI SDK 的原生中止原语就是 `abortSignal`；仓库内转发链路（base-agent.ts:108-114）与 abort 后干净返回（:224-226，有回归测试）已经存在，per-run 复位是唯一缺失件，改动最小、语义最正。这也让既有但未接线的 RPC `abort_controller` 与 app.tsx 的 Ctrl+C 路径一并变正确。

### 手工端到端复演

1. `npm run build && node dist/cli.js`（或 dev 流程），发一条长回答问题。
2. 流式中按 ESC：输出立即停止；聊天区出现部分文本 + `⏹ interrupted` + `⊘ Response interrupted by user.`；spinner 消失。
3. 立刻发第二条消息：controller 正常新回合作答（证明未哑火、无并发回合错乱）；回答内容体现"知道上一轮被打断"（不把半截输出当完整结论）。
4. `cat ~/.wayang/sessions/<sid>/conversation.jsonl | tail -3`：能看到截断 assistant 条目（`interrupted:true`）与 `subtype:"interrupted"` 标记。
5. controller 流式期间有 worker 在跑（先派个长任务再提问 controller）：按 ESC 后 worker 状态栏不动、任务继续，随后其完成信号被正常汇报。
6. 发消息后立刻按 ESC（首个 token 前）：不出现空 assistant 消息，只有 `⊘` 标记行。
7. Ctrl+C（busy 时）：与 ESC 同效（顺带修复的旧路径）。

## 6. 验收标准

1. ESC 在 busy 时立即停止流式输出与思考（下一个渲染帧内），且绝不触碰 worker 任务。
2. 已产出文本以一条 `interrupted: true` 的 assistant 条目保留；零输出时无 assistant 条目。
3. 每次中断在 conversation.jsonl 有 `subtype:"interrupted"` 标记；下一回合的 LLM 请求消息序列中含 `[USER INTERRUPT] …`（getMessages 可验证）。
4. 中止后的下一回合功能完整（非哑火）；`npm run lint`、`npm test`、`npm run build` 全绿。
5. 中断记录在会话 resume（`--resume`）后仍可见。

## 7. 非目标

- 不重构流式渲染、消息存储或输入框其他行为（ESC 清空草稿、选区/建议面板优先级均维持现状）。
- 不做"ESC 同时取消 worker 任务"（那是 `/cancel` 与 cancel_task 的职责）。
- 不打断 controller 工具的本地执行（工具完成即回合收敛）。
- 不保留中断时刻的部分 reasoning（textStream 之外无来源，见 §3.4）。
- 不改 RPC 协议、SignalQueue 语义、CHANGELOG.md（合并时统一补）。
- 不引入独立的 interrupt 事件流文件。
