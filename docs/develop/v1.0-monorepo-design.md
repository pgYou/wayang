# Wayang 1.0 分包架构设计（Monorepo）

> 状态：定案，作为 1.0.0 实施蓝本。本文只记录最终方案与关键理由，不保留讨论过程。
> 关联：`CHANGELOG.md` 的 v1.0.0 规划段；实施分支 `feat/100-monorepo`。

## 1. 目标与原则

1.0 的两个交付物共用一套逻辑内核：

- **npm 包 `wayang-ai`**：命令行产品（`wayang` / `waya`），发布链路与 0.9.x 完全一致；
- **Wayang Desktop**：Electron 桌面产品，安装包分发，不走 npm。

支撑目标的三条架构原则：

| 原则 | 含义 |
|---|---|
| 行为一致性 | 每个包的运行时代码**编译恰好一次**；任何交付物里的同一段代码出自同一次构建 |
| 宿主归应用 | core 不选择进程模型（依赖倒置）：进程宿主与通信策略由各 app 自定 |
| 发布单点 | 对外只有 `wayang-ai` 一个 npm 包；所有子包 private、永不发布 |

## 2. 目录结构

```
wayang-ai/                      ← workspace root，也是 npm 发布单元（见 §6）
├── apps/                       ← 应用包：可独立交付的构建边缘
│   ├── cli/                    ← 终端产品（TUI + stdio 宿主）
│   └── desktop/                ← Electron 产品（UtilityProcess 宿主）
└── packages/                   ← 库包：编译一次、被 apps 消费产物
    ├── core/                   ← 逻辑内核（服务端 + 客户端 SDK）
    └── protocol/               ← 类型 + RPC framing + transport
```

root `package.json` 的 `workspaces: ["apps/*", "packages/*"]`。

## 3. 包定位与依赖方向

```
protocol ◀── core ◀──┬── cli（apps）
                     └── desktop（apps）      apps 之间零依赖
```

| 包 | 名称 | 职责 | 依赖 |
|---|---|---|---|
| protocol | `@wayang-ai/protocol` | 共享类型；RPC 消息定义（METHOD/NOTIFY/RpcError）；RpcClient/RpcServer；流式 transport + MessagePort transport | 无 |
| core | `@wayang-ai/core` | 逻辑内核：WayangServer/Supervisor/engine/agents（服务端）；RemoteSupervisor 等客户端 SDK；MCP bridge（编译与寻址，内部资产） | protocol |
| cli | `@wayang-ai/cli` | 终端产品：TUI、stdio 宿主、npm 发布产物载体 | core、protocol |
| desktop | `@wayang-ai/desktop` | 桌面产品：Electron 壳、UtilityProcess 宿主、渲染层 UI | core、protocol |

core 的对外形态是**函数入口**：`runWayangServer(options, io)`，`io` 为可注入的
`{ stdin, stdout }` 流。进程策略（spawn / UtilityProcess / 测试内嵌）完全由调用方决定；
`options.mcpBridgeEntryPath` 可注入 MCP bridge 路径（经 SystemContext 传递），不传时
按「宿主入口同目录」兜底（见 §4.1）。

## 4. 构建模型

### 4.1 库包（packages/*）：编译恰好一次

- tsup `preserveModules: true`：`dist/` 镜像 `src/` 目录结构；
- `tsc -p tsconfig.build.json` 产出相邻 d.ts；
- exports 指向产物（子路径 import 全仓零改动）：

```json
"exports": {
  ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" },
  "./*": { "types": "./dist/*.d.ts", "default": "./dist/*.js" }
}
```

- **兄弟包之间 external**：core 的构建不内联 protocol，引用其 dist——保证任何一段
  运行时代码只存在一份编译输出；
- 判据：**有运行时代码且被 ≥2 个异构工具链边缘直接 import 的包必须构建**。protocol
  含 RPC 状态机（组帧、分发、超时语义），协议层分叉是最恶劣的不一致，故与 core 一同
  构建。纯类型、零运行时代码的包可豁免为源码直出（当前没有这样的包）。
- **MCP bridge 是 core 的内部运行期资产**：core 的 tsup 双入口——库产物之外，
  `mcp-bridge-entry.js` 平铺产出在 `core/dist/` 根。运行期寻址顺序：SystemContext
  注入的 `mcpBridgeEntryPath` ▶ 宿主入口同目录 ▶ 源码候选（开发/测试直跑兜底）。
  bridge 对 app 只是一个待复制的文件，无任何语义知识（见 §4.2）。

### 4.2 应用包（apps/*）：宿主 + 内联

每个 app = 库产物 + 自己的宿主胶水 + 自己的构建契约，一次性编成自己的交付物：

| | cli（tsup） | desktop（electron-vite） |
|---|---|---|
| 入口 | `cli.js`（TUI）、`server-entry.js`（stdio 宿主） | main、preload、renderer、`utility-entry.js`（MessagePort 宿主） |
| 对库的处理 | `noExternal: [/^@wayang-ai\//]`，读库 dist 内联 | electron-vite resolve 到库 dist 后内联 |
| 输出 | ESM，node20 | 全 ESM（要求 Electron ≥ 28） |

两条固定规则：

1. **app 机械复制 bridge**：构建后把 `packages/core/dist/mcp-bridge-entry.js` 复制到
   宿主入口所在目录（cli 用构建脚本 copy；desktop 用 extraResources 直接取）。这是纯
   文件搬运，app 不需要理解 bridge 是什么；复制遗漏由门槛断言兜底——产物目录中该文件
   必须存在，缺失即构建期失败，不留到运行期。
2. **全 ESM 纪律**：所有产物 ESM 输出。`import.meta.url` 等模块格式敏感代码只在
   ESM 下有定义；任何边缘输出 CJS 即为事故。

### 4.3 构建拓扑（Turborepo）

构建顺序成为硬约束（cli/desktop 的 lint/test 依赖库 dist 存在），由 turbo 编排：

```jsonc
// turbo.json（v2 语法）
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "lint":  { "dependsOn": ["^build"] },
    "test":  { "dependsOn": ["^build"] }
  }
}
```

- root scripts 从 `--workspaces` 委托切换到 `turbo run build / lint / test`；
- **陈旧产物纪律**：所有门槛一律经 `turbo run`，靠输入哈希失效保证「测到的就是当前
  源码编译出的产物」，禁止绕过 turbo 直接跑下游包脚本；
- CI 顺序相应调整：`npm ci → turbo run lint test build`（lint/test 隐式前置库构建）。

## 5. 运行时拓扑

### 5.1 CLI

```
TUI 进程（cli.js）
  └─ spawn node server-entry.js ── stdio ── WayangServer（core）
                                        └─ bridge 路径交 ACP agent spawn
                                           （bridge 已复制到宿主同目录）
```

- 通信：`createStreamTransport(stdin, stdout)` + RpcClient + RemoteSupervisor（core 提供）；
- 退出协议：SHUTDOWN RPC → 5s 宽限 → SIGKILL；server 意外死亡 → 终端报错退出。

### 5.2 Desktop

```
Electron main（壳 + RPC 客户端）
  ├─ utilityProcess.fork(utility-entry.js) ── MessagePort ── WayangServer（core）
  │                                                    └─ bridge 路径交 agent spawn
  │                                                       （extraResources 已复制到宿主同目录）
  └─ renderer（UI）── IPC ── main
```

- 通信：protocol 提供 MessagePort↔流 适配 transport，RPC 帧与 CLI 完全同协议；
  RemoteSupervisor 对传输无感；
- **PATH 修复**：GUI 启动的进程无用户 shell PATH，而 server spawn ACP agent 依赖
  PATH——app 启动时构造完整 PATH，逐层继承。这是 desktop 壳的固定职责；
- 生命周期：`before-quit` 走与 CLI 相同的退出协议；server 崩溃时提示一键 resume
  （session/resume 语义现成），不退出应用。

## 6. 发布模型（保持 0.9.x 链路）

- **发布单元是 root**：`wayang-ai`，npm 上唯一暴露的包；
- `bin`：`wayang` / `waya` → `apps/cli/dist/cli.js`；
- `files`：`["apps/cli/dist", "!apps/cli/dist/**/*.map"]`——server 宿主入口与 bridge
  （复制进入）已含在 cli 产物内，无需额外目录；
- 子包全部 `private: true`，任何情况下不发布；
- prerelease 版本按首段自动 dist-tag（`1.0.0-alpha.0` → `alpha`，`rc`/`beta` 同理），
  防止顶掉 `latest`；
- desktop 走 electron-builder 安装包（dmg/exe 等），extraResources 拷贝 desktop 自己
  构建的 utility-entry 与 bridge。

## 7. 边界规则（check-boundaries.mjs）

| 规则 | 内容 |
|---|---|
| 依赖方向 | protocol 不依赖任何兄弟；core 只依赖 protocol；apps 依赖 core+protocol |
| apps 互斥 | cli 与 desktop 互不 import、互不引用对方产物 |
| renderer 限制 | desktop 渲染层只许 import protocol 的类型 + 自身 IPC 层；禁止 core（Node 内建依赖进浏览器环境必炸） |
| 宿主归属 | 进程宿主代码（spawn/utilityProcess/生命周期）只存在于 apps，库内禁止 |

## 8. tsconfig 策略

- root `tsconfig.base.json` 单点定义全部语义项（target/module/jsx/strict 等）；
- 各包 tsconfig 只保留：`extends` + `paths`（依赖方向映射）+ include/exclude + 环境差异
  （如 renderer 的 DOM lib）；
- 这是 ESM 纪律之外的一致性防线：库只编译一次，但 apps 各自的宿主/UI 代码仍由
  各自工具链编译，语义项共享杜绝分叉。
