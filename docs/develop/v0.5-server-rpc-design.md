# v0.5 设计:逻辑进程化 + RPC + 测试体系

> 状态:已定稿,实施中
> 对应路线图:0.5 架构地基(版本级路线图已并入 [README](../../README.md#roadmap))

## 1. 背景与目标

当前逻辑层(Supervisor 及其全部服务)与 ink TUI 同进程,零 RPC 痕迹;测试只有单测(手写 vi.mock),无 e2e。本版把逻辑层抽成**无头独立进程**,任何 UI 通过统一 RPC 驱动,并以同一接口建立 e2e。

**目标:**
1. `wayang server` 无头逻辑进程:承载 Supervisor 全部职责,进程内零 ink/react 依赖。
2. RPC v1(stdio 传输;协议传输无关,WS 留给 0.6 WebUI):命令面 + 状态订阅面。
3. TUI 瘦身为瘦客户端:基础对话 + `/tasks` 摘要 + inquiry 应答;删除 worker-list-overlay、worker-detail-page、路由。
4. e2e 体系:fake OpenAI 兼容 provider(按请求内容路由的脚本回放)+ harness,3 个核心场景。
5. GitHub Actions CI:lint + 单测 + build + e2e。
6. 行为不变的纯重构:用户可感知功能不增不减(除 TUI 收缩项)。

**非目标(明确不做):**
- WebSocket 传输与鉴权(0.6 随 WebUI 落地,协议保持传输无关)。
- 多客户端并发接入语义(0.6;本版 stdio 单客户端)。
- WebUI、任务编号、任务组(后续版本)。
- worker 会话详情查看(TUI 删除,不迁移)。

## 2. 架构

### 2.1 进程拓扑

```
┌─────────────────────────┐        spawn        ┌──────────────────────────┐
│  wayang(CLI/TUI 进程)  │ ──────────────────► │  wayang server(逻辑进程)│
│  meow 解析/onboard/     │    stdio JSON-RPC   │  Supervisor 全家:        │
│  会话选择(交互留在客户端)│ ◄────────────────── │  SignalQueue/Engine/     │
│  ink 渲染 RemoteSuper.  │   命令 + 状态事件    │  ControllerAgent/Loop/   │
└─────────────────────────┘                     │  Skills/SessionManager   │
                                                │  (零 ink/react 依赖)      │
                                                └──────────────────────────┘
```

- **交互留在客户端**:onboard、`--resume` 交互选择、sessionless 继承判定都是客户端完成,把*结论*(new / resume:id)作为参数传给 server;server 无任何交互提示。
- **e2e 与 TUI 走同一接口**:测试直接 spawn `wayang server`,以 RPC 驱动,天然覆盖 TUI 所依赖的全部协议。
- 崩溃隔离:server 崩溃不影响终端;客户端退出(Ctrl+C×2 / `/exit`)发送 `shutdown` 命令,server 优雅关停;SIGTERM 兜底(沿用现有 handler)。

### 2.2 模块布局(新增)

```
src/rpc/
  protocol.ts        # 消息类型 + 方法名常量(双端共享)
  transport.ts       # 帧编解码 + 任意双工流的读写器(传输无关)
  rpc-server.ts      # 命令分发 + 订阅管理 → 写通知
  rpc-client.ts      # 请求/响应配对 + 通知分发 + 远程 Subscribable 缓存
src/server/
  wayang-server.ts   # 无头核心:loadConfig(非交互)→ Supervisor 生命周期 + 命令实现
  main.ts            # `wayang server` 入口:参数解析 → 起 server
src/client/
  remote-supervisor.ts  # TUI 侧门面:呈现与 Supervisor 相同的消费面
e2e/
  fake-provider.ts   # OpenAI 兼容 SSE 脚本回放(按请求内容路由)
  harness.ts         # spawn server + RPC 客户端 + 事件收集/断言工具
  scenarios/*.test.ts
```

## 3. RPC 协议 v1

传输无关;0.5 用 **stdio,换行分隔 JSON**(每行一条)。预留:WS 上同样的消息集,0.6 加鉴权。

### 3.1 消息

```ts
// 客户端 → 服务端(请求)
{ id: number, method: string, params?: object }
// 服务端 → 客户端(响应)
{ id: number, result?: unknown } | { id: number, error: { code: number, message: string } }
// 服务端 → 客户端(通知,无 id)
{ method: string, params: object }
```

错误码:`-32601` 未知方法;`-32000` 服务端内部错误;`4000+` 业务错误(带 message)。

### 3.2 生命周期通知

- `ready` `{ sessionId, sessionDir, workspaceDir }` — Supervisor restore+start 完成后发出,此前到来的请求排队。

### 3.3 命令面(客户端 → 服务端)

| 方法 | 参数 | 结果 | 说明 |
|---|---|---|---|
| `submit_input` | `{ text }` | `{}` | user input 信号 + sessionManager.onUserInput |
| `resolve_inquiry` | `{ answer }` | `{}` | controller 的 inquire 应答 |
| `list_tasks` | `{ status? }` | `TaskDetail[]` | engine.list |
| `cancel_task` | `{ taskId }` | `{}` | engine.cancel |
| `update_task` | `{ taskId, updates }` | `{}` | engine.updatePending |
| `respond_permission` | `{ requestId, approved, reason? }` | `{}` | engine.resolvePermission |
| `chat_worker` | `{ workerId, message }` | `{}` | engine.sendMessageToWorker |
| `dispose_worker` | `{ workerId }` | `{}` | engine.abortByWorkerId |
| `perform_compaction` | `{}` | `{}` | controllerAgent.performCompaction |
| `abort_controller` | `{}` | `{}` | controllerAgent.abort(Ctrl+C 打断) |
| `get_status` | `{}` | `{ sessionId, busy, running, pending, activeWorkers }` | 概要(客户端启动横幅/状态栏兜底) |
| `get_snapshot` | `{ target, path }` | `{ data }` | 任意 Subscribable 目标的路径快照 |
| `subscribe` | `{ target, path }` | `{ subscriptionId, data }` | 订阅;**返回即时快照** |
| `unsubscribe` | `{ subscriptionId }` | `{}` | 退订 |
| `shutdown` | `{}` | `{}` | supervisor.shutdown 后进程退出 |

**Subscribable 目标**(`target`):`controllerAgent` / `signalQueue` / `engine` / `sessionManager`。

### 3.4 订阅语义(关键设计)

`BaseWayangState.notify` 的事件 `data` **永远是订阅路径下的全量值**(纯 JSON,本就持久化)。因此:

- 服务端 `subscribe`:同步完成 `getSnapshot(path)` → `subscribe(path, cb)`(JS 单线程,两步之间无插入),响应携带快照;此后 `state.event` 通知流:`{ subscriptionId, target, path, data }`。
- 客户端按 `path` 维护**本地缓存**(`Map<path, data>`):快照与事件都是全量覆盖,天然幂等、无需增量合并;`getSnapshot` 本地命中,不产生网络往返。
- 顺序保证:stdio 严格有序,服务端同步转发,客户端按到达顺序覆盖 → 最终一致。

流式文本(`dynamicState.streamingEntries`)每 chunk 一次 set → 事件量较大,但均为小 JSON,本地 stdio 可承受;0.6 WS 接入前再考虑节流(设计已预留:客户端缓存层可加 debounce,不影响协议)。

## 4. Server 侧

### 4.1 `WayangServer`(src/server/wayang-server.ts)

职责:非交互 `loadConfig` → 按参数构造 Supervisor(`restore()+start()`)→ 把命令面映射到 supervisor 内部 → 发 `ready`。

命令实现全部一行式委托(见上表),错误统一捕获为 `{code:-32000, message}`。

### 4.2 `wayang server` CLI(src/server/main.ts + cli.ts 分发)

```
wayang server --config <path> --home-dir <dir> --workspace-dir <dir> \
  --session new|resume:<id> --inject-previous-tasks --log-level <level>
```

- `cli.ts`:`input[0] === 'server'` 时转发(其余 flags 与主命令一致)。
- server 进程内 `loadConfig` 非交互:配置缺失直接报错退出(客户端 onboard 时已落盘/env 继承,正常不会触发)。
- stdio 上的任何日志**不得污染 RPC 通道**:pino 日志只写文件(sessionDir/wayang.log,现状如此),进程 stderr 只放致命错误摘要。

### 4.3 客户端启动流(bootstrap 改造)

`bootstrap()` 保留:loadConfig(交互 onboard)→ fresh/`--resume`/sessionless 判定(现状逻辑)→ **不再 new Supervisor**,改为:

1. `spawnServer(resolved)`:`node <cli.js> server …`(同一 bin,execPath+argv[1]);
2. 连接 `RpcClient`(child.stdin/stdout),等 `ready`;
3. `new RemoteSupervisor(rpc)` 交给 `renderInkUI`;
4. ink 退出钩子:`shutdown` RPC + 2s 后 SIGKILL 兜底。

## 5. TUI 瘦身

**删除:** `pages/worker-detail-page.tsx`、`components/worker-list-overlay.tsx`、`providers/route-provider.tsx`、`/worker` 命令与路由跳转。
**保留/调整:** ControllerPage(对话主体)、InquiryPrompt、StatusBar、`/tasks`、`/cancel`、`/compact`、`/exit`、`/help`;`/workers` 从 overlay 降级为文本列表(activeWorkers 快照)。
**接入:** `SupervisorProvider` 的值类型改为 `RemoteSupervisor`(src/client/remote-supervisor.ts),消费面与原 Supervisor 对 TUI 暴露的完全一致:

```ts
controllerAgent: RemoteSubscribable & { abort(); performCompaction() }
signalQueue:     RemoteSubscribable & { enqueue(sig) }
engine:          RemoteSubscribable & { list(status?); cancel(id); getActiveWorkers() }
sessionManager:  { onUserInput(text) }
resolveInquiry(answer); shutdown()
```

## 6. 测试体系

### 6.1 单测(vitest,现状模式)

- `src/rpc/__tests__/`:协议帧编解码;rpc-server 用假核心测分发/订阅/错误;rpc-client 用内存双工流对(两个 transport 直接对接)测请求配对、通知、缓存收敛。
- `src/server/__tests__/wayang-server.test.ts`:临时目录 + `vi.mock` model-factory(沿用 base-agent.test.ts 手法),断言命令→信号/任务落库。
- 既有 35 个测试文件保持绿(重构不动行为)。

### 6.2 e2e(vitest 独立工程,`npm run test:e2e`)

**fake provider**(`e2e/fake-provider.ts`):本地 HTTP 服务,实现 `/v1/chat/completions` SSE。**按请求内容路由**:脚本条目带 `match(requestBody)`(依据 system prompt 特征区分 controller / worker / summarizer),每条含 `{ text? , toolCalls?: [{ name, args }] }`;请求到达取**首个 match 且未消费**的条目回放。避免"controller 下一步请求与 worker 首请求竞态"导致的顺序不确定性。

**harness**(`e2e/harness.ts`):临时 homeDir/workspaceDir → 写 config(endpoint 指 fake provider)→ spawn `node dist/cli.js server` → RPC 连接 → `waitSignal(type, predicate)` / `waitSnapshot(path, predicate)` 断言工具。

**场景:**
1. **single-task**:`submit_input` → controller(add_task)→ worker(update_progress → done)→ completed 信号 → controller 文本收尾。断言:任务 history=completed、会话含工具调用与最终回复。
2. **permission**:任务含 `chmod 644 /tmp/wayang-e2e-perm.txt`(命中危险命令模式)→ worker bash 被中间件拦截 → `permission_request` 信号 → e2e 调 `respond_permission(approved)` → bash 真实执行 → done → completed。断言:权限信号出现且被批准后任务完成、文件权限变化。
3. **multiStage**:add_task(multiStage)→ done 后 worker 停 idle → `submit_input` 二段指令 → controller(add_task assignToWorker)→ 同 worker 完成二段 → 两个 completed 信号同一 workerId。

并发固定 1,消除并行竞态;每个场景整体超时 60s。

### 6.3 CI(`.github/workflows/ci.yml`)

push/PR 触发,ubuntu + node 20:`npm ci` → `lint` → `test` → `build` → `test:e2e`(e2e 依赖 dist)。

## 7. 兼容与迁移

- 会话数据/目录结构零变化;`--resume`/`--fresh`/sessionless 行为不变。
- `wayang`(默认)对外无感:仍是交互式终端应用;差异仅内部多一个子进程。
- 退出语义:Ctrl+C 一次=打断 LLM(abort_controller),双击=shutdown+exit(与现状一致)。

## 8. 风险

| 风险 | 对策 |
|---|---|
| 拆分引入行为回归 | e2e 先行:场景先行跑在旧架构?不 —— 协议面即测试面,harness 只依赖 server 二进制;先实现 server(包旧 Supervisor)再拆客户端,单步验证 |
| stdio 被 console 污染 | 服务端禁用 console;pino 仅写文件;CI 加"协议帧必须是合法 JSON"校验(transport 层实现即保证) |
| 流式事件洪泛 | 本地 stdio + 小 payload 可承受;缓存层可 debounce;0.6 前实测再定 |
| fake provider 与 AI SDK 格式漂移 | e2e 即探针:SDK 升级导致解析变化会立刻红;SSE 按 OpenAI 官方 chunk 格式构造 |
