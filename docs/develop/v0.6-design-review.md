# v0.6 设计评审

元信息：

- 评审对象：docs/develop/v0.6-design.md（草案，未修改）
- 评审日期：2026-10-30
- 代码基线：package.json 0.5.2；ai 6.0.218；claude-agent-sdk 0.2.98
- 评审方式：设计文档与相关源码逐条对照，涉及 SDK 内部语义的结论以 node_modules 实读为准，无法实读的标注为推断
- 路径核对：文中引用行号已在当前基线实读核对；无法确认的行号保留 [待复核] 标注，不作猜测

## 结论摘要

0.6 的方向成立：2a（补话时效）与 2b（worker 主动提问）都是修复正确性问题，不是功能叠加。但存在 2 个会导致直接出错的实现级风险，且 WAY-N 编号建议移出本版本。建议将 0.6 收敛为纯 2a + 2b。

## 一、严重问题（会直接出错）

### 1.1 interrupt 可能撞上悬挂的 permission 等待

现象：immediate 模式下，worker 若正处于 canUseTool 的 permission 等待，此时调用 interrupt() 打断，行为不可从代码证明。

证据：src/services/agents/claude-code-worker.ts:320-327（已核对：该区间为 `return new Promise<PermissionResult>` 起至 `_pendingPermissions.set(requestId, { resolve, timer })`，即 permission 等待的悬挂点；interrupt 与该 promise 的交互无法从代码推出）。

后果：推断（待 PoC 验证），两种坏情况——留下孤立的 tool_use 导致下一轮 API 报错；或 permission promise 永不结算，任务永久挂起。

建议：immediate 模式下检查 pending permission，非空则排队到 resolve 之后再 interrupt；或限定只在文本流阶段打断，工具执行期间排队到 tool_result 之后。

### 1.2 进程内 MCP 工具的默认超时可能掐死 ask_controller

现象：设计 §6.3 用 createSdkMcpServer 注册 ask_controller，而该工具要阻塞等待 controller 应答，最长 5 分钟。

证据：claude-agent-sdk 的 MCP 工具默认超时为数秒到数十秒级（推断，待 PoC 验证）。

后果：提问半路被 SDK 杀掉，worker 拿到超时错误而非 controller 答案，2b 在 Claude 侧直接不可用。

建议：实现前必须 PoC 验证；若属实，显式配置该工具超时，或改走与 permission 相同的宿主回调通道，而非 MCP 工具。

## 二、中等问题（会退化或难排查）

### 2.1 prepareStep 每步重新注入是必要且安全的（原疑点不成立）

现象：原担心注入消息被 SDK 并入历史导致重复累积。

证据：ai 6.0.218 每步基准为 `stepInputMessages = [...initialMessages, ...responseMessages]`（node_modules/ai/dist/index.mjs:4522；原稿所引 4508 经核对落在 responseMessages 的 tool-result 累积区段，与该机制一致），prepareStep 的 messages 覆盖仅作用于当次请求（index.mjs:4539-4540，`prepareStepResult?.messages ?? stepInputMessages`）。

后果：不重复累积。但注入内容必须同时写入 state.conversation 的 User entry，否则跨 stage 不存活（src/services/agents/context-manager.ts:104-112，getMessages 每次从 state 的 conversation 重建消息）。

建议：实现时两条路径都写，缺一即出现"当前任务能收到、进入下一 stage 就丢"的隐蔽 bug。

### 2.2 任务收尾窗口内的消息静默丢弃（本次要修的核心 bug，比文档描述更窄也更精确）

现象：inbox 不持久化，不存在 resume 重放问题；真正的洞在收尾窗口。

证据：src/services/agents/worker-state.ts:50-53（已核对：持久化路径仅含 runtimeState 与 conversation，inbox 仅存在于初始内存数据）；handleDone 收尾检查之后，removeWorkerTracking 用 setTimeout(0) 延迟删除 worker（src/services/task-execute-engine.ts:924-929），此窗口内 sendMessageToWorker 仍返回 true（src/services/task-execute-engine.ts:275-280）。

后果：消息投进一个即将消失的 worker，静默丢失，而 chat_worker 回报成功——这就是文档说的"说谎"，但根因是状态判定，不是投递通道。

建议：投递前检查 activeWorkers 状态而非 workers Map 的存续；chat_worker 的返回值改为反映真实状态。

### 2.3 inquiry 超时无回报

现象：pending inquiry 纯内存保存，worker 崩溃即失。

证据：src/services/task-execute-engine.ts:350 [待复核]（阻塞占并发槽；经核对，task-execute-engine.ts 全文未检索到 inquiry 相关逻辑，350 行实际落在 scheduleNext 的并发槽占用循环，pending inquiry 的真实存放位置待确认）

后果：worker 超时后自行继续，controller 侧没有任何信号被告知；只有等到 respond_inquiry 返回 false 才发现问题。

建议：超时主动发 inquiry_timeout 信号；对已消失的 worker 返回结构化错误而非 false。

### 2.4 旧任务 description 内嵌已废弃工具指引

现象：prompt 每次 spawn 现建，重启后 running 任务被判定失败，所以"prompt 层"不会残留旧指引。

证据：src/services/agents/worker-agent.ts:52-55（每次构造 worker 时调用 buildWorkerSystemPrompt 现建 prompt）、src/services/task-execute-engine.ts:936-943（recoverCrashedTasks 将 running 任务判为失败）

后果：残留风险来自任务 description 文本里内嵌的"定期调用 check_controller_messages"类指引，会反复调用已删除的工具。

建议：删除工具时保留一版返回 "deprecated" 的占位实现，至少跨一个 minor 版本。

## 三、轻微问题（体验/可维护性）

### 3.1 问答审计缺失

证据：worker 侧对话记录不回读（src/services/agents/claude-code-worker.ts:5-14，已核对：注释明确 "written for UI display and audit only — never read back"），且问答不进入 worker conversation（src/services/agents/claude-code-worker.ts:395-401 [待复核]，经核对该区间为 handleAssistantMessage 的文本抽取，未能直接证明问答条目不落 conversation）。

建议：即便审计放 controller 侧，也向 worker conversation 落一条 System entry，便于事后复盘。

### 3.2 inquiry 与 permission 的交互错配风险低（原疑点不成立）

证据：请求 id 全局唯一并按 id 遍历匹配（src/services/task-execute-engine.ts:283-290，resolvePermission 按 requestId 遍历匹配），abort 时两处清理幂等（src/services/agents/claude-code-worker.ts:250、src/services/task-execute-engine.ts:387）。

结论：不需要额外的仲裁机制，但两条链路仍建议抽成共用的"阻塞请求"抽象，避免逻辑复制后漂移。

## 四、WAY-N：建议移出 0.6，延后单独实现

理由：

1. 收益已被覆盖。短后缀体系已存在且在用：shortId = id.slice(-4)（src/tui/utils/text-width.ts:74-75），permission 行与 worker 句柄均使用（src/tui/utils/permission-summary.ts:268-269、src/tui/components/chat-area/signal-row.tsx:38）。
2. 成本不成比例。workspace 级计数器引入持久化、跨进程丢更新、损坏自愈、旧条目回退四类新问题；其中跨进程是实证问题而非假设——src/infra/session-index.ts:5-8 明确支持多进程并发，设计文档 docs/develop/v0.6-design.md:37 的单进程论证不充分。
3. 性质不同。2a/2b 是正确性修复（静默丢消息、无提问通道），WAY-N 是展示优化，混在同一版会分散评审与回归注意力。

替代方案（可行，两者都不落盘）：

- 复用短后缀：零新成本，缺点是不含时间序语义。
- 展示层按 createdAt 排序编号：TaskDetail 已有 createdAt（src/services/tools/add-task.ts:66），只读不写，无并发问题；代价是跨 session 需读全 workspace 任务文件（与自愈扫描同量级只读成本），同毫秒并列需 id 字典序 tie-break。

建议 0.6 先用短后缀，排序序号后续作为纯展示层增强。

## 五、收敛后的范围与验收标准

范围：仅 2a（补话时效）+ 2b（worker 主动提问）。不做 WAY-N。

验收标准（每条可客观判定）：

1. 注入在场性单测：注入后，逐条断言每一轮发给模型的 messages 尾部仍含该指令，且同一条指令不重复出现两次以上。
2. 无消息零覆盖单测：inbox 为空时 prepareStep 返回 undefined，实际请求的 messages 与未启用该选项时逐字节相等。
3. 静默丢弃 e2e：任务完成瞬间队列仍有未读消息，controller 收到 message_undelivered，chat_worker 不再返回虚假的 delivered。
4. 工具执行中收指令 e2e：长耗时 bash 期间发送指令，任务要么读到并继续、要么干净失败；进程无未捕获异常，abort 后 pending Map size = 0。
5. inquiry 四路径单测：正常 resolve / 超时返回 [TIMEOUT] 并继续 / abort 时全部 resolve 且清理干净 / 迟到的 respond_inquiry 返回 false。
6. 全环 e2e：worker 提问 → controller 应答 → worker 完成，带超时上限，全程无死锁。

## 六、实现前必须先做的 3 个验证

1. PoC：canUseTool pending 期间、以及工具执行中调用 interrupt()，确认是否留下孤立 tool_use 及下一轮真实行为，据此确定安全插入点。（对应 1.1）
2. PoC：进程内 MCP 工具 execute 阻塞超过默认超时是否被掐断，确定 ask_controller 的实现通道。（对应 1.2）
3. e2e：多步任务中断言 prepareStep 注入消息在场且幂等，作为后续 SDK 升级的哨兵测试雏形。（对应 2.1）
